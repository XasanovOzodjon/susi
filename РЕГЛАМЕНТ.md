# Регламент команды из сессий Claude Code — v2

> **Что нового в v2:** память между чатами (Claude-mem) и граф кода (TencentDB Agent Memory) — §8.1;
> гейт pentester через Claude Security — §5.1; профессиональный выкат через Forgejo (скан образов,
> закрытый реестр, доставка по digest, кольцо откатов) — §5.2 и §11.2; телефон — только резервный канал — §3.2.

Документ для одного разработчика, который хочет работать командой из нескольких сессий Claude Code.
Его можно взять в любой проект как есть: имена, адреса и ключи здесь заменены заглушками
`<вот такими>`.

Регламент вырос из живой работы над реальным проектом. Почти каждое правило появилось после
конкретной дорогой ошибки, поэтому пояснение «почему» стоит рядом с правилом.

Рядом лежит набор для запуска:

| Файл | Что это |
|---|---|
| `team.conf` | список ролей сетки: имя, папка, ветка |
| `roles/*.md` | стартовый промпт каждой роли |
| `bus.sh` | файловая шина: heartbeat, чтение ящика по курсору, письмо, ACK |
| `launch-team.sh` | запуск сетки в tmux (Linux, macOS, WSL) |
| `launch-team.ps1` | запуск сетки в Windows Terminal |

---

## 0. Идея в одном абзаце

Одна сессия Claude Code делает всё и быстро теряет нить. Несколько сессий, у каждой своя ось и
свои запреты, проверяют друг друга. Код пишут одни, на безопасность смотрит другая сессия, а
прод проверяет третья. Чтобы это работало, нужны пять вещей:

1. **Роли**: у каждой сессии есть предмет, за который она отвечает, и список того, чего она не делает.
2. **Связь**: письмо доходит гарантированно, и отправитель знает, что оно дошло.
3. **Доска задач**: видно, кто что держит и на каком шаге.
4. **Путь коммита**: каждая правка до прода проходит ветку, тест, гейт и выкат.
5. **Слово владельца**: деньги, прод и необратимые действия выполняются только по прямому «да» человека.

---

## 1. Роли

Шесть универсальных ролей. Для маленького проекта хватит трёх: orchestrator, backend и pentester.
Остальные роли поднимаются под задачу и гасятся после неё.

| Сессия | Держит | Не делает |
|---|---|---|
| **orchestrator** | картина целиком, доска задач, связь с владельцем через Telegram, выкат в `main` | не проверяет сам себя на безопасность; чужие задачи за других не ведёт |
| **backend** | серверный код, база, миграции, интеграции | экраны и прод-сервер; в `main` не пушит |
| **frontend** | интерфейс, вёрстка, e2e-тесты | бэкенд, миграции, `.env`, прод; в `main` не пушит |
| **devops** | CI, раннер, сервер, деплой, мониторинг, логи | продуктовый код |
| **qa** | сценарии человека на проде и стенде, дефекты с доказательством (скрин, шаги) | не чинит, только находит и заводит задачу |
| **pentester** | гейт безопасности на каждый коммит (вердикт привязан к sha), приёмка после выката | сам не патчит |

Правила состава:

1. **Один предмет — один исполнитель.** Если нужна правка на чужой оси, заведи задачу с тегом
   хозяина и напиши ему, а сам не правь. *Почему:* две сессии в одном файле дают конфликт, и
   согласование выходит дороже кода.
2. **Одно имя — одна живая копия.** Две сессии под одним именем ломают адресацию: одна дочитала
   ящик, а вторая этих писем уже никогда не увидит.
3. **Свой git worktree на роль.** У каждой роли своя папка и своя ветка `w/<роль>/…`.
   *Почему:* три сессии в общем дереве однажды свалили свои коммиты на одну ветку.
4. **Простой роли — это норма.** Сессия без задачи ждёт и не ищет себе работу. *Почему:* роли,
   которые «дежурили», находили мета-работу (проверки проверок) и сжигали лимит подписки впустую.
5. **Больше ролей — дороже.** Если сессии пишут друг другу больше, чем пишут код, сократи состав.
   Если задачи ждут оркестратора дольше, чем делаются, расширь его.

## 2. Принципы проверки

1. **Замер, а не догадка.** Число или имя, на котором держится вывод, записывается вместе с
   командой, которая его дала, и с именем того, кто её запустил. Без этого пиши «со слов X».
2. **Проверяй то, что реально исполнится.** Код на проде смотри в `git grep … origin/main`, а не в
   рабочем дереве. Вердикт гейта даётся на конкретный sha.
3. **Тест доказывает правку, только если умеет краснеть.** Убери правку одним словом, и тест должен
   упасть, причём по правильной причине, а не от синтаксической ошибки. Если не упал, доказательства нет.
4. **Отказ прибора — ещё не вердикт.** «Пусто», «0» или «200» могут значить, что прибор не сработал.
   Рядом с искомым ищи значение, которое заведомо существует, тем же способом.
5. **У проверки три исхода:** «да», «нет» и «судить нечем». Третий исход сообщается громко.
6. **Граница вердикта называется вслух:** что вердикт НЕ покрывает.
7. **Честность владельцу.** Пиши результат или «застряли на X, нужно Y, срок Z». Ошибся — скажи
   первым, до того как это всплывёт.

## 3. Связь

Каналов три, у каждого своя задача.

### 3.1 Файловая шина — для того, что нельзя потерять

Это папка с текстовыми файлами (`~/bus` или `C:\bus`). Канон протокола — `bus.sh` и этот раздел.

```
bus/
  inbox/<имя>.md      личный ящик: другие сессии дописывают сюда письма
  outbox/<имя>.md     мои отправленные письма, которые ждут ACK
  presence/<имя>      heartbeat: время изменения файла показывает, жива ли сессия
  cursor/<имя>.read   номер строки, до которой я дочитал ящик
  cursor/<имя>.seen   id писем, которые я уже обработал
  handoffs/<имя>.md   капсула роли для смены чата (§8)
  ALERTS.md           «адресат офлайн, доставьте руками»
```

Пять правил. Каждая сессия выполняет их на **каждом своём ходу**:

1. **Heartbeat первым делом:** `./bus.sh beat <имя>`. Команда `./bus.sh who` показывает, кто жив.
2. **Читать ящик по курсору, а не грепом:** `./bus.sh read <имя>`. Скрипт отдаёт все строки после
   курсора с нахлёстом в 10 строк, а повторы отбрасывает по id.
   *Почему:* поиск по шаблону `-> имя` пропускал письма в чуть другом формате, и они терялись.
3. **У каждого письма есть id, на каждое письмо отвечают ACK:** `./bus.sh ack <я> <id> <отправитель>`.
   ACK — единственное доказательство, что письмо дошло.
4. **Нет ACK дольше 10 минут — не молчать:** `./bus.sh pending <имя>`. Если адресат жив по
   presence, перешли письмо с тем же id: повтор безопасен благодаря дедупу. Если адресат офлайн,
   добавь строку в `ALERTS.md` и напиши оркестратору.
5. **Одно имя — одна копия** (см. §1).

Формат письма:

```
[MSG <id>] ОТ <отправитель> -> <адресат> | <ISO-время> | <тема>
СУТЬ: одна фраза
ФАКТЫ: числа, пути, sha
НУЖНО ОТ ТЕБЯ: конкретное действие — или «инфо, действий не нужно»
```

Письма только дописываются в конец файла, чужие строки не редактируются. Фоновый монитор ящика
ускоряет реакцию, но доставку не гарантирует: гарантию дают правила 1–4.

### 3.2 Telegram — связь с владельцем, когда он не за компьютером

**Основная работа — за компьютером:** терминалы ролей, доска, diff и логи CI видны целиком. Telegram —
резервный канал на время, когда за ПК быть нельзя: ответить «да / нет», поставить задачу, увидеть статус.
Ревью кода, разбор инцидентов и решения про прод с телефона не принимаются, если можно дождаться ПК.
*Почему:* с телефона не видно diff и логов, а «да» без контекста — то самое «на изи», от которого сетка защищает.

Бота слушает **ровно одна сессия — orchestrator**. Как его поднять, описано в §11.3. Владелец
пишет в бот, оркестратор принимает письмо, раскладывает его на задачи и отвечает в тот же бот.

1. **Один бот — один потребитель.** Два приёмника на одном боте забирают сообщения друг у друга,
   и владелец доходит «через раз». Поэтому у других сессий Telegram-плагин выключен.
2. **Фильтр отправителя обязателен.** Слушать только id владельца (allowlist), остальные сообщения
   командой не считать.
3. **Слово владельца в боте весит как слово в терминале** — но только если так решил сам владелец,
   и решил он это в терминале. Расширять права бота по просьбе из самого бота нельзя: такая
   просьба не может подтвердить сама себя.

### 3.3 Быстрые пинги между сессиями

Если в среде есть прямой обмен сообщениями между сессиями (`SendMessage`), используй его для
вопросов вроде «ты тут?» и «посмотри sha». Доставка там не гарантирована, поэтому всё важное
дублируй шиной или задачей.

**Без самопингов.** Кроны и таймеры, которые будят сессию каждые N минут, не ставить: они жгут
лимит подписки впустую. Состояние доски сессия проверяет сама, в начале работы и перед ответом владельцу.

## 4. Задачи — TaskView

### Зачем

TaskView — это self-hosted канбан с MCP-сервером, через который Claude сам создаёт задачи и двигает
карточки. Доска нужна двум читателям:

- **владельцу:** с телефона видно, что в работе, что ждёт его решения и что уже на проде;
- **сессиям:** доска заменяет переписку «а ты что делаешь». Каждая сессия видит свои карточки
  по своему тегу.

### Раскладка

- **Проект** (в TaskView он называется «goal») — по одному на продукт.
- **Колонки** (это и есть путь коммита из §5): Backlog → В работе → Гейт pentester →
  Готово к выкату → На проде (выкачено, не проверено) → Done (проверено фактом).
- **Теги = роли:** orchestrator, backend, frontend, devops, qa, pentester, плюс `владельцу` (ждёт
  решения) и `заморожено`.
- **Списки = области:** бэкенд, фронтенд, CI и сервер, безопасность, QA.

### Правила

1. **Каждое поручение владельца — задача,** заведённая в тот же ход и ДО работы. Мелкие тоже.
   В заметке задачи: дословная цитата, время, канал; затем СУТЬ / ФАКТЫ / ГОТОВО КОГДА.
2. **Номер в названии:** «TV-N · …». Ответ владельцу начинается с «TV-N», чтобы с телефона было
   видно, о чём речь.
3. **Каждый шаг двигает колонку.** Доказательства (sha, прогон, замер) дописываются в заметку,
   прежний текст не затирается. В Done попадает только то, что проверено фактом.
4. **Взял задачу — поставь срок.** Сорвал срок — перенеси и напиши причину. Задача ждёт другую —
   поставь зависимость.
5. **Решение за владельцем** — тег `владельцу` и заголовок «Владельцу: …».
6. **Владелец может поручать перетаскиванием.** Если твоя карточка оказалась в «В работе», а ты её
   не брал, значит владелец отдал её тебе. Бери.

## 5. Путь коммита до прода — Forgejo

### Зачем Forgejo

Forgejo — это self-hosted git-хостинг (форк Gitea) со встроенным CI, Forgejo Actions, который
совместим с синтаксисом GitHub Actions. В сетке он делает три вещи:

1. **Хранит код и ветки.** `main` равен проду: пуш в `main` запускает деплой.
2. **Гоняет CI** на каждый пуш: тесты, сканеры уязвимостей и деплой.
3. **Защищает `main`** правилом ветки (protected branch), чтобы туда не попадали коммиты мимо гейта.

Issues в Forgejo можно использовать как второй трекер для задач, которые касаются нескольких
проектов (например, общая безопасность), но основная доска проекта — TaskView.

### Шаги

1. **Ветка** `w/<тема>` от свежего `origin/main` (сначала `git fetch`). Файлы добавляются поимённо,
   `git add -A` не используется никогда.
2. **Тест плюс мутант** (см. §2.3). Сборка запускается последней, после правки всех файлов.
3. **Пуш ветки и сообщение pentester:** sha, от какого коммита, что сделано, чем проверено.
   Карточка уходит в «Гейт».
4. **Замечания закрываются новым коммитом** в ту же ветку и снова идут на гейт с новым sha.
   В `main` force-push запрещён.
5. **PASS → выкат.** Выкат — это fast-forward `main`. Если `main` ушёл вперёд, сделай cherry-pick и
   сверь `git patch-id --stable`: если patch-id совпал, вердикт переносится. Выкатывает тот, в чьём
   канале прозвучало «да» владельца.
6. **Приёмка живьём.** Проверь, что на проде нужный sha (например, `/build-sha.txt`) и `/healthz`
   отвечает 200. Потом проверь саму правку. Только после этого карточка уходит в Done с
   доказательством.
7. **Откат.** Деплой сам откатывается, если упала миграция или healthz. Для ручного отката —
   revert-коммит. Самый быстрый откат — флаг в `.env`, поэтому новое поведение лучше прятать за флагом.

### 5.1 Гейт pentester — Claude Security

Pentester гейтит каждый sha плагином **Claude Security** (`claude-security@claude-plugins-official`):

1. Установка один раз: `/plugin install claude-security@claude-plugins-official`.
2. На каждый sha — скан изменений ветки относительно `origin/main` (`/claude-security` → «scan changes»).
   Находки плагин сам перепроверяет панелью агентов; в вердикт идут только подтверждённые.
3. Вердикт — как в §9: PASS / FAIL / СУДИТЬ НЕЧЕМ + sha + чем доказано + граница. Отчёт скана — ссылкой в карточку.
4. Плагин умеет готовить патчи, но pentester их **не применяет**: находка уходит задачей хозяину оси.
   *Почему:* проверяющий, который сам чинит, начинает проверять свой код и подыгрывать.
5. Раз в неделю или перед крупным релизом — полный скан репозитория, находки — задачами с тегом `безопасность`.

Claude Security не заменяет сканеры CI (§5.2): он смотрит логику кода, сканеры — зависимости и образы.

### 5.2 Выкат через Forgejo — профессиональная схема

Пример живой схемы (прод вне приватной сети, образы ему привозит раннер):

1. **Пуш в `main`** запускает `deploy-main.yml` на отдельном раннере, который берёт только `main`.
2. **Проверки кода:** тесты, guard, сканы кода. Любое красное — дальше не идёт.
3. **Сборка и скан образов:** каждый образ собирается в файл `.tar`, и **trivy сканирует именно этот файл**.
   Скан блокирующий.
4. **Проверка реестра перед пушем:** реестр обязан отказывать без входа (401 / 403 / 404). Любой другой
   ответ — стоп: значит, реестр открыт. Аккаунт реестра — скрытый.
5. **Пуш в реестр** того же просканированного файла, без пересборки (например, `crane push`).
   Записываются digest и отпечаток образа в `ops/images-<sha>.txt`.
6. **Доставка на прод по digest, никогда по тегу** (тег можно подменить): раннер скачивает образ
   и передаёт на прод (`ssh … docker load`), рядом с кодом кладёт список ожидаемых образов.
7. **Выкат:** сначала сверка отпечатков, только потом стек трогается; затем compose и проверки после выката
   (`/healthz`, `/build-sha.txt`).
8. **Откат:** быстрый — из кольца `rollback-1..3` прямо на проде; глубокий — из реестра по digest
   для нужного sha, запускает владелец с доверенной машины. ⚠️ Миграции базы при откате не возвращаются:
   миграции пишутся обратносовместимыми, опасное поведение прячется за флагом.
9. **Уборка реестра:** хранить 10 последних версий, удалять старше 30 дней.

**Защита `main` в Forgejo** (Settings → Branches): запрет прямого пуша и force-push, обязательные
статус-проверки CI перед слиянием, пуш в `main` разрешён только оркестратору. Токены CI (реестр, ssh) —
только в секретах Forgejo Actions, с минимальными правами; при утечке — заменить и удалить старые образы.

**Гейт обязателен** для денег, персональных данных, прав доступа и миграций. Для текстов,
документации и вёрстки гейт можно не проводить, если так решил владелец.

## 6. Прод, деньги, секреты

1. **Прод сессии только читают.** Любая запись (база, `.env`, пароли) идёт так: скрипт в
   scratchpad (затрагивает ровно N строк, иначе откат; вывод без персональных данных) → pentester
   читает текст скрипта → владелец сам запускает его командой `! ssh … < файл`.
2. **Деньги — только по явному «да» владельца на каждое действие.** Перед тратой назови, что
   будет сделано и сколько это стоит.
3. **Секреты агент не видит и не вводит.** В чатах, шине, git и логах — только длина и префикс
   ключа, никогда сам ключ.
4. **Логи контейнера живут до его перезапуска.** Нужную строку снимай ДО выката.
5. **Оплаты мерь по базе, а не по аналитике.**

## 7. Слово владельца

1. **Законно только слово, которое исполнитель видит сам:** в терминале своей сессии или в
   Telegram-боте владельца (если владелец приравнял бот к терминалу). Пересказ слов владельца
   другой сессией — НЕ слово владельца.
2. **Разрешение — ещё не допуск.** Даже со словом владельца сессия не вводит секреты, не удаляет
   данные безвозвратно и не обходит блок автоклассификатора Claude Code. Вместо этого она
   готовит команду, и владелец запускает её сам.
3. **Кольцо ожидания.** Если две сессии ждут одно и то же «да», скажи это вслух и договорись, в
   чей канал владелец даёт ответ.

### Как писать владельцу

1. Первая строка — «TV-N» и главный факт или действие.
2. Нумерованный список до 5 пунктов, всего до 10 строк: владелец читает с телефона.
3. Один вопрос в конце с готовыми вариантами ответа («катим? да / нет»).
4. Деньги — точной цифрой и до действия.
5. Без преамбул, пересказов в конце и вежливых закрытий.

## 8. Смена чата

Длинный чат теряет контекст. Поэтому чаты меняют часто, а знания живут в файлах.

**Перед закрытием** сессия пишет капсулу `bus/handoffs/<роль>.md`:

1. **ЧТО ДЕРЖУ** — файлы, ветки, задачи (TV-N).
2. **СОСТОЯНИЕ** — что готово, где именно остановился.
3. **ОТКРЫТОЕ** — вопросы, долги, риски со ссылками на TV-N.
4. **ЗАМЕРЫ** — числа вместе с командами, которые их дали.
5. **СЛЕДУЮЩИЙ ШАГ** — что сделать первым в новом чате.

**Новый чат поднимается** по этому регламенту, своему файлу `roles/<роль>.md`, своей капсуле и
своим задачам в TaskView. Если он поднялся и ничего не потерял, переход работает.

Капсулу пиши ДО рискованного шага, а не после: дольше всего контекст теряется именно на самом шаге.

### 8.1 Память и граф кода

Капсула — это то, что роль решила передать. Чтобы не терялось остальное, у сетки две памяти:

1. **Claude-mem** (плагин `claude-mem@thedotmack`) — автоматически сохраняет наблюдения каждой сессии
   (решения, правки, находки) и подмешивает их в новый чат. Поиск по прошлой работе — его MCP-поиск.
   Установка: `/plugin marketplace add thedotmack/claude-mem`, затем `/plugin install claude-mem`.
   *Почему:* «мы это уже чинили?» без памяти стоит час раскопок или повторной ошибки.
2. **Граф кода — TencentDB Agent Memory, часть Code-Graph** (github.com/TencentCloud/TencentDB-Agent-Memory, MIT).
   Разворачивается отдельно и подключается как MCP (`claude mcp add <проект>-code …`). Роль спрашивает
   у графа «где вызывается X, что сломается, если поменять Y», а не читает файлы подряд.
   *Почему:* чтение всего проекта сжигает контекст и лимит подписки, а граф отвечает адресно.
3. **Порядок источников:** регламент и `roles/<роль>.md` → своя капсула → задачи TaskView → Claude-mem →
   граф кода → сами файлы. Память — подсказка, а не замер: факт перед вердиктом проверяется по §2.

## 9. Машина и лимиты

1. **Каждая сессия ест память.** Лишние копии сессий и неиспользуемые MCP-серверы — главные
   пожиратели. Не поднимай больше ролей, чем нужно сегодня.
2. **Кэши сборки** (go, npm, playwright) держи на диске, где есть место, а не на системном.
3. **Лимит подписки тратится на переписку.** Писать адресно (не «всем»), отвечать в три строки:
   ```
   ВЕРДИКТ: PASS / FAIL / СУДИТЬ НЕЧЕМ, sha
   ЧЕМ ДОКАЗАНО: замер, число, контроль
   ГРАНИЦА: чего вердикт НЕ покрывает
   ```

## 10. Запуск сетки

### 10.1 Что делает лаунчер

1. Читает `team.conf`: роли, их папки и ветки.
2. Для каждой роли, кроме orchestrator, создаёт git worktree `../<проект>-wt/<роль>` на ветке
   `w/<роль>/main`, если его ещё нет.
3. Создаёт ящики шины `bus/inbox/<роль>.md`.
4. Даёт каждой роли постоянный id сессии (`.team/sessions/<роль>.id`). При первом запуске
   используется `claude --session-id <id>`, при следующих `claude --resume <id>`. Поэтому сетка
   после перезагрузки компьютера поднимается с той же историей.
5. Собирает промпт роли `.team/sessions/<роль>.prompt.md` из `roles/<роль>.md` и подставляет в
   него абсолютные пути к шине и `bus.sh`. *Почему:* в worktree роли нет папки `.team`, поэтому
   относительный путь там не сработает.
6. Открывает все сессии на одном экране. Каждой сессии передаётся имя (`--name <роль>`) и её
   промпт (`--append-system-prompt-file`).
7. Только orchestrator запускается с Telegram-каналом
   (`--channels plugin:telegram@claude-plugins-official`).

При первом запуске каждая панель спрашивает «Is this a project you trust?». По умолчанию выбрано
«No, exit», поэтому в каждой панели выбери «Yes, I trust this folder». Дальше вопрос не повторяется.

Папку `.team/sessions/` добавь в `.gitignore`: там лежат id сессий конкретной машины.
Повторный запуск лаунчера, когда сетка уже открыта, создаст вторые копии сессий. Сначала закрой
старые окна (bash-версия в этом случае просто подключается к уже открытой сессии tmux).

### 10.2 Linux, macOS, WSL — `launch-team.sh` (tmux)

```bash
cd ~/my-project
cp -r ~/Сетка-Claude/{team.conf,roles,bus.sh,launch-team.sh} .team/   # один раз
DRYRUN=1 .team/launch-team.sh    # показать команды и ничего не запускать
.team/launch-team.sh             # поднять сетку; tmux attach -t team, если сессия уже есть
```

### 10.3 Windows — `launch-team.ps1` (Windows Terminal)

```powershell
cd C:\work\my-project
$env:TEAM_DRYRUN = '1'; .\.team\launch-team.ps1; Remove-Item Env:TEAM_DRYRUN   # показать команды
.\.team\launch-team.ps1                                                       # поднять сетку
```

Для `bus.sh` на Windows нужен Git Bash: Claude Code на Windows и так работает через него.
Шина по умолчанию лежит в `C:\bus`, другой путь задаётся переменной `BUS_DIR`.

Грабли Windows, которые скрипт уже обходит:

- PowerShell 5.1 читает `.ps1` без BOM в кодировке cp1251, и кириллица в коде ломает разбор.
  Поэтому скрипт написан только ASCII-символами.
- Путь с кириллицей в `cmd /k` иногда молча не открывается. Скрипт передаёт папку параметром
  Windows Terminal (`-d`), а не командой `cd`.
- `wt split-pane` с позиционными аргументами путал роли местами. Скрипт передаёт роль внутри
  команды каждой панели явно.

## 11. Установка инструментов

Порядок установки: Claude Code → Claude-mem и Claude Security (плагины) → шина → TaskView → Forgejo →
граф кода → Telegram. Без TaskView и Forgejo
сетка тоже работает: задачи можно вести в Issues любого git-хостинга, а CI — на GitHub Actions.

### 11.1 TaskView (доска)

1. Поднять TaskView Community Edition по README репозитория `Gimanh/taskview-community`
   (docker compose). Образы закрепить по `@sha256`.
2. Сразу сменить пароль администратора, закрыть регистрацию и открыть доступ только из своей
   сети (например, через Tailscale).
3. В TaskView выпустить API-токен.
4. Подключить MCP (подставить свой адрес; токен в командах и файлах проекта не светить):
   ```bash
   npm install --prefix ~/.claude/mcp-servers/taskview taskview-mcp@<версия>
   claude mcp add taskview -s user \
     -e TASKVIEW_URL=http://<хост>:1725 -e TASKVIEW_TOKEN=<токен> \
     -- node ~/.claude/mcp-servers/taskview/node_modules/taskview-mcp/dist/index.js
   ```
5. Создать проект, колонки, теги и списки из §4. Их id записать в `CLAUDE.md` проекта, чтобы
   сессии не угадывали номера.

### 11.2 Forgejo (код и CI)

1. Поднять Forgejo в docker (`codeberg.org/forgejo/forgejo:<версия>`) и Forgejo Runner для
   Actions. Раннер лучше держать на отдельной машине: job-контейнеры с доступом к docker socket
   фактически имеют root на хосте.
2. Создать репозиторий, сделать `main` защищённой веткой и запретить force-push.
3. Написать `.forgejo/workflows/deploy-main.yml` по схеме §5.2: тесты и сканы кода → сборка образов в `.tar`
   → блокирующий trivy → проверка, что реестр закрыт → пуш того же файла → доставка по digest → сверка
   отпечатков → выкат → проверки после выката → автооткат.
4. Защитить `main` (Settings → Branches): без прямого пуша и force-push, обязательные статус-проверки,
   пуш только оркестратору. Секреты CI — только в Actions secrets, раннер — отдельный и только для `main`.
5. Включить реестр пакетов Forgejo (скрытый аккаунт) и правило уборки: 10 версий, старше 30 дней — удалять.
6. Подключить MCP (по желанию, для Issues и чтения CI):
   ```bash
   claude mcp add forgejo -s user \
     -e FORGEJO_URL=http://<хост>:3000 -e FORGEJO_TOKEN=<токен> \
     -- npx -y @ric_/forgejo-mcp
   ```

### 11.3 Telegram (резервный канал, когда нет ПК)

1. В Telegram открыть @BotFather, отправить `/newbot`, задать имя и username (он должен
   заканчиваться на `bot`). BotFather пришлёт токен вида `123456789:AA…`.
2. Поставить Bun: на этом рантайме работает MCP-сервер канала.
3. В любой сессии Claude Code установить плагин:
   ```
   /plugin install telegram@claude-plugins-official
   /telegram:configure <токен>
   ```
   Токен сохранится в `~/.claude/channels/telegram/.env`.
4. Перезапустить ТОЛЬКО orchestrator с каналом (лаунчер делает это сам):
   ```bash
   claude --channels plugin:telegram@claude-plugins-official
   ```
5. Написать боту в личку. Он ответит кодом из 6 символов. В сессии выполнить
   `/telegram:access pair <код>`.
6. Закрыть доступ всем остальным: `/telegram:access policy allowlist`.
7. Проверить: отправить боту «ping». Сессия должна ответить в чат. Фото, отправленные боту,
   сохраняются в `~/.claude/channels/telegram/inbox/`, и сессия может их прочитать.

⚠️ Истории сообщений Bot API не отдаёт: то, что пришло, пока orchestrator был выключен, не
восстановится. Если нужна полная гарантия, держи orchestrator запущенным.

⚠️ Нужен второй бот на той же машине (например, для другого проекта)? Направь переменную
`TELEGRAM_STATE_DIR` на отдельную папку для каждого бота.

### 11.4 Память и граф кода

1. Claude-mem: `/plugin marketplace add thedotmack/claude-mem` → `/plugin install claude-mem` → перезапустить сессии.
2. Claude Security: `/plugin install claude-security@claude-plugins-official` (нужен pentester).
3. Граф кода: развернуть TencentDB Agent Memory по его `INSTALL.md` (нужна часть Code-Graph), проиндексировать
   репозиторий и подключить как MCP: `claude mcp add <проект>-code -s user -- <команда из INSTALL.md>`.
   Адреса и ключи — заглушками, в файлы проекта не класть.

### 11.5 Шина

```bash
./bus.sh init                 # создать папки и ящики для всех ролей из team.conf
./bus.sh who                  # кто жив
```

Строку «на каждом ходу: `./bus.sh beat <роль>` и `./bus.sh read <роль>`» положить в
`CLAUDE.md` проекта. Её подхватит каждая сессия.

## 12. Сетка работает, если

1. `./bus.sh who` показывает все роли со свежим временем.
2. Письмо от backend к pentester получает ACK меньше чем за 10 минут.
3. Сообщение владельца в бот превращается в карточку TaskView с номером, а ответ начинается
   с «TV-N».
4. Коммит проходит путь «ветка → тест с мутантом → гейт → выкат → приёмка» и попадает в Done
   с доказательством.
5. После закрытия всех окон и повторного запуска лаунчера каждая роль продолжает со своей историей.
6. Новый чат роли отвечает «что решили вчера по TV-N» из Claude-mem, не перечитывая файлы.
7. Каждый sha в «Гейте» имеет отчёт Claude Security, а в `ops/images-<sha>.txt` — digest того образа, что на проде.
